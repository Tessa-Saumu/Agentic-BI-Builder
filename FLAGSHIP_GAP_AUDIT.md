## Executive Summary

Agentic BI Builder is a strong flagship candidate: the core idea (typed LangGraph workflow → real SQL execution → bounded LLM repair → deterministic PBIR/TMDL compiler) is coherent, the code is substantive (~4,900 lines of production code plus ~2,900 lines of tests), and ownership is attributable (117 candidate commits, 9 mentor commits, 7 of them merges). The compiler's 119 tests encode real Power BI Desktop constraints, and the retry budget is enforced by graph topology rather than a state counter — these are genuine engineering choices, not checkbox artifacts.

However, a recruiter who clones the repo today will hit credibility blockers within the first two minutes: `pip install -r requirements.txt && pytest` produces **198 passed, 18 errors**; no license exists; dependencies are unpinned and include four unused packages; the evidence artifacts the README result tables cite (profiles, KPIs, reflection JSONs, stress-test outputs) are gitignored and not in the tree; the README still has the placeholder clone URL `github.com/your-username/agentic-bi-builder`; and there is no public, runnable demonstration — the repo is private, nothing is deployed, and the end-to-end "opens in Power BI Desktop" claim requires Windows + API keys, which a portfolio reviewer cannot execute. No CI has ever run.

The project is **not broken** — the deterministic compiler pipeline works and the test suite is well-designed — but the *evidence layer* (reproducibility, public proof, honest limits, contribution boundaries) is thinner than the engineering layer. The backlog below closes that gap without turning v1 into v2.

A special note on the private-repo constraint: because the repository is being kept private during development, the flagship package must include a **public demonstration surface** — either a small public demo repo, a deployed Streamlit preview (using deterministic offline mode so it does not require API keys), or a clearly-hosted static evidence page — so a recruiter can see the system working without being granted repo access. That is a portfolio packaging issue, not a rebuild.

## Explicitly Out of Scope

The following items are tempting but should **not** be done as part of the flagship consolidation. Each would turn this from a consolidation into a rebuild, expand scope past v1's bounded claim, or duplicate effort already covered by other portfolio projects:

1. **V2 explorer rework (issues #15–#39):** Multi-table joins, stateful multi-turn exploration, relationship detection, hierarchy generation, a "data explorer" mode, streaming output, and the broader grammar support described in the 25 open V2 issues. Finish v1 first; v2 is a separate project, not a polish step.
2. **Streamlit UI for the actual agent:** README already lists a Streamlit UI as a stretch goal that was intentionally descoped. A lightweight *deterministic demo* Streamlit app for public proof (G11) is in scope; building a full interactive Streamlit frontend for live LLM runs is not.
3. **Power BI Service publishing / scheduled refresh / gateway integration:** This is explicitly out of scope per `docs/Project Description.md` and would require Windows Server / Azure infrastructure that cannot be meaningfully demonstrated in a portfolio.
4. **Replacing the regex SQL→DAX translator with a full SQL parser (e.g., sqlglot):** A tempting engineering upgrade, but the fail-closed semantics and tested shape set are v1's explicit design choice. Widening DAX support is a v2 feature; closing the two small documented gaps (G20) is v1 polish, not a parser replacement.
5. **Docker containerization:** Power BI Desktop is Windows GUI software and cannot run in a Linux container. Containerizing the CLI adds nothing reproducible that `pip install -r requirements.txt` + pinned deps does not already provide, and gives a false impression of portability. Not recommended as a checkbox.
6. **Cloud deployment of the agent as an API:** Adding FastAPI + a hosted endpoint would change the project from a local CLI tool into a service, raise security/prompt-injection/cost concerns that are out of v1 scope, and duplicate the API/deployment story already told by the Customer Churn Prediction & BI Platform flagship.
7. **Fine-tuning or training a custom model:** The project is about *applied LLM workflow engineering*, not model training. There is no dataset of ground-truth KPIs to train on (and G23's small pilot does not create one). Adding fine-tuning would misframe the project's capability.
8. **RAG / retrieval-augmented KPI suggestions / documentation lookup:** This is a plausible v2 feature but adds a whole subsystem (vector store, chunking, retrieval evaluation) that v1 does not need to demonstrate bounded-agent engineering.
9. **Adding more datasets beyond the three reference sets:** Three structurally different domains (music retail, e-commerce, HR) already demonstrate the bounded scope. Adding more datasets does not strengthen evidence unless it is tied to the G23 evaluation.
10. **Rebuilding the candidate-owned frontend for this project:** This is a CLI + compiler project; the portfolio's frontend evidence can come from StudyGapAI only if/when that project is repaired, not by bolting a UI onto Agentic BI.
11. **Kubernetes / Terraform / cloud-infrastructure-as-code:** No deployment exists; infra for a non-existent deployment is pure checkbox work.
12. **Authentication / multi-user support:** This is a single-user local tool. Auth is the Churn platform's story.
13. **Erasing all evidence of mentor contributions or rewriting history to make the project appear solo-authored:** The mentor commits are part of a legitimate mentorship story. Credit them explicitly (G13) instead.
14. **A large benchmark / timing study across many providers / temperature sweeps:** One traceable live run with recorded settings is sufficient for v1 claims (see Flagship Definition of Done). Repeated benchmarks are a v2 measurement effort.
15. **Acquiring patient-level data / rebuilding a medical classifier / adding a CV component:** That is the Alzheimer's supporting project, not this one.
16. **Converting the project to claim production use, users, or enterprise deployment:** It has none of those, and honestly stating "mentored portfolio project, v1" is stronger than inflating scope.

## Flagship Definition of Done

The project is ready to be presented as a **public flagship** when every item below is true. This is a finite checklist — not a roadmap for perfection.

### Reproducibility
- [ ] `git clone <real-url> && pip install -r requirements.txt && pytest` runs **all tests green (0 errors, 0 failures)** on a fresh virtualenv with only the documented Python version, with no manual prerequisite steps.
- [ ] Dependencies are pinned (major.minor or exact) and dead dependencies are removed; `pytest` is in requirements; supported Python version is stated.
- [ ] GitHub Actions CI runs the full test suite on every push to `main`; the CI badge in README is green; CI fails the build on non-zero exit from `run_agent.py`.
- [ ] `scripts/profile_datasets.py` and all other `scripts/run_*` drivers work on a fresh clone against the committed dataset filenames (no silent skips).
- [ ] A LICENSE file is present (MIT recommended).
- [ ] `fix_structure.sh` is removed, disabled, or prominently labeled as a historical scaffold script that must not be run.

### Core system correctness
- [ ] The deterministic end-to-end path (profiler → executor → compiler → `.pbip`) runs on all three committed datasets and produces structurally valid output, verified by an automated no-network regression test (G9).
- [ ] Graph wiring and the one-retry-no-loop topological property are verified by automated tests (G10).
- [ ] `run_agent.py` exits with non-zero status when a report is not written or when errors are present; CI catches this (G7).
- [ ] The min-visual build gate (reject reports with fewer than 4 translatable visuals) is exercised by an automated test.
- [ ] Broken-KPI drop semantics are exercised by an automated test.

### Evidence
- [ ] A committed evidence bundle exists under a named directory (e.g., `evidence/v1/`) containing profiles, KPI specs, reflection logs, and stress-test outputs for at least one full live-provider run, plus a `metadata.json` recording date, provider, exact model identifiers, decoding settings, package versions, and Python version.
- [ ] README result tables and timing numbers cite the committed evidence bundle; any numbers from historical runs not in the bundle are labelled as historical with a date and the explicit caveat that artifacts are not attached.
- [ ] Model identifiers are consistent across `.env.example`, `llm_client.py`, and README; `temperature` is set consistently or the asymmetry is documented.
- [ ] Fault-injection results are presented with in-line denominators (e.g., "12/12 planted faults caught in this round (2 datasets × 3 fault types); 6/12 categorised as an adjacent but defensible category") rather than as a flat "24/24" claim.
